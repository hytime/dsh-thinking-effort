## 中文

感谢你为本仓库贡献代码。本仓库是 DSH（DeepSeek Harness）的第三方插件 `@hytime/dsh-thinking-effort`。

### 分支模型

本仓库用 `dev` 作为**集成分支**，`main` 是**发布源**：

```text
你的 PR ──base──> dev ──测试通过, 由维护者合入──> main ──打 tag──> 发布
```

- **外部 PR 一律以 `dev` 为 base**，不要以 `main` 为 base。
- `dev` 上的改动经 CI 验证后，由维护者合入 `main`。
- `main` 只接收来自 `dev` 且测试通过的代码，是唯一的发布源。
- 发布由维护者操作：在 `main` 上打 `v*.*.*` tag 会触发发布 workflow。**不要自己改版本号或打 tag。**

提交 PR 前请先把分支 rebase 到最新 `dev`。过旧的 base 会产生"能无冲突合并、但语义已经错了"的结果——例如把新条目并进一个已经发布的版本段落。

### 提交 PR

1. Fork 本仓库，从最新 `dev` 切出主题分支：`git checkout -b fix/your-topic dev`
2. 按 [PR 模板](./.github/PULL_REQUEST_TEMPLATE.md) 填写描述。模板会在你开 PR 时自动载入。
3. 一个 PR 只做一个逻辑改动，保持改动聚焦。
4. 在 PR 页面勾选 **Allow edits from maintainers**，方便维护者帮你 rebase。

### 提交前自查

- **不要改 `package.json` 的 `version`** —— 发版是维护者动作。
- **只改 `src/`**：`lib/` 是 `pnpm run build` 的产物，已被 gitignore，不要手改、不要提交。
- **只暂存显式路径**：用 `git add <路径>`，不要用 `git add .` / `git add -A`。
- **CHANGELOG 条目只加在 `[Unreleased]` 段**，不要改动已发布版本的段落。
- 涉及用户可见行为或配置改动时，同步四语言文档：`README.{md,zh,ja,ko}.md`、`docs/INSTALL.{md,zh,ja,ko}.md`、`docs/CHANGELOG.{md,ja,ko}.md`。
- 本地规划产物（`docs/superpowers/`、`.superpowers/`）**禁止提交**。

### 门禁

CI 在 Node `22.19.0` 与 `24.x` 两个版本上跑同一套 `quality` 门禁。合入前本地至少跑一遍：

```bash
pnpm install --frozen-lockfile
pnpm run build
pnpm run typecheck
pnpm run typecheck:test
pnpm test
pnpm run test:release
node --check lib/index.js
node --check lib/client.js
pnpm pack --dry-run
git diff --check
```

此外仓库还有一个 CI job `pr-policy`，它检查 PR 的 base、版本号、生成产物与 CHANGELOG 归属。**它只提示、不阻止合并**：问题以 workflow 注解与 Step Summary 的形式给出。请尽量处理它报告的问题，尤其是 CHANGELOG 归属。

### 本地规划文件

`docs/superpowers/` 与 `.superpowers/` 只用于本地计划、简报与审查产物，必须持续被 `.gitignore` 忽略。提交前确认索引里没有它们：

```bash
test -z "$(git ls-files docs/superpowers .superpowers)"
```

### 报告问题

用 [bug 表单](https://github.com/hytime/dsh-thinking-effort/issues/new?template=bug_report.yml) 提交 issue，填写版本、操作系统、Node 版本与最短复现步骤。

## English

Thanks for contributing. This repository is the third-party DSH (DeepSeek Harness) plugin `@hytime/dsh-thinking-effort`.

This file is for human contributors. The repository's full rules and mechanisms live in [AGENTS.md](./AGENTS.md) and win on conflict; that file addresses coding agents working in this repository.

This file covers the branch model, PR flow, and merge gates. It deliberately does **not** repeat install, upgrade, verification, or release procedures — AGENTS.md owns those.

### Branch model

This repository uses `dev` as the **integration branch** and `main` as the **release source**:

```text
your PR ──base──> dev ──tests pass, maintainer merges──> main ──tag──> publish
```

- **Open external PRs against `dev`**, never against `main`.
- Changes on `dev` are merged into `main` by a maintainer once CI is green.
- `main` only receives code that came through `dev` and passed its tests, and is the only release source.
- Releases are a maintainer action: pushing a `v*.*.*` tag on `main` triggers the publish workflow. **Do not bump the version or push tags yourself.**

Rebase your branch onto the latest `dev` before opening the PR. A stale base produces changes that merge without conflict but are already semantically wrong — for example, an entry appended to an already published version's changelog section.

### Opening a pull request

1. Fork the repository and branch off the latest `dev`: `git checkout -b fix/your-topic dev`
2. Fill in the description following the [PR template](./.github/PULL_REQUEST_TEMPLATE.md), which GitHub loads automatically.
3. Keep one PR to one logical change.
4. Tick **Allow edits from maintainers** on the PR so a maintainer can rebase for you.

### Before you submit

- **Do not change `version` in `package.json`** — releases are a maintainer action.
- **Change `src/` only**: `lib/` is generated by `pnpm run build` and gitignored; do not hand-edit or commit it.
- **Stage explicit paths only**: use `git add <path>`, never `git add .` / `git add -A`.
- **Add changelog entries under `[Unreleased]` only**; never edit a published version's section.
- When user-visible behavior or configuration changes, update all four languages: `README.{md,zh,ja,ko}.md`, `docs/INSTALL.{md,zh,ja,ko}.md`, `docs/CHANGELOG.{md,ja,ko}.md`.
- Local planning artifacts (`docs/superpowers/`, `.superpowers/`) **must not be committed**.

### Gates

CI runs the same `quality` gates on Node `22.19.0` and `24.x`. Run at least these locally before merging:

```bash
pnpm install --frozen-lockfile
pnpm run build
pnpm run typecheck
pnpm run typecheck:test
pnpm test
pnpm run test:release
node --check lib/index.js
node --check lib/client.js
pnpm pack --dry-run
git diff --check
```

A `pr-policy` CI job additionally checks the PR's base, version bump, generated artifacts, and changelog placement. **It warns without blocking**: findings appear as workflow annotations and a step summary. Please address them, especially changelog placement.

### Local planning files

`docs/superpowers/` and `.superpowers/` hold local plans, briefs, and review artifacts, and must stay gitignored. Confirm the index is clean before committing:

```bash
test -z "$(git ls-files docs/superpowers .superpowers)"
```

### Reporting issues

Use the [bug form](https://github.com/hytime/dsh-thinking-effort/issues/new?template=bug_report.yml) and include the version, operating system, Node version, and minimal reproduction steps.
